# Architecture

## Canonical V1 request path

Memory Service is organized into modules for memory, retrieval, knowledge,
learning, and jobs. The active HTTP application is Express (`src/app.ts`);
controllers delegate memory operations to the container's `store` and `recall`
functions.

```text
                   Client
                      │
                      ▼
              Express controllers
                      │
                      ▼
             Memory / retrieval pipeline
        ┌─────────────┼─────────────┐
        │             │             │
        ▼             ▼             ▼
    Memories     Knowledge      Learning
        │             │             │
        ▼             ▼             ▼
      Qdrant    Knowledge Graph   Feedback
```

## Main Components

### Memory and retrieval

`POST /memory` and `POST /memory/search` are the canonical memory API paths.
`MemoryRepository` is the canonical Qdrant adapter and always uses
`config.memoryCollection`. Embeddings are generated by Ollama before storing or
searching.

Responsibilities:

* Store memories
* Semantic search
* Semantic storage and retrieval
* Duplicate detection and keyword-index updates
* Importance and confidence metadata

### Context

Builds the prompt sent to the LLM.

Responsibilities:

* Search
* Ranking
* Filtering
* Compression
* Prompt generation

### Knowledge

Transforms memories into structured knowledge.

Responsibilities:

* Knowledge extraction
* Consolidation
* Knowledge graph
* Inference
* Explanation
* Conflict resolution

### Learning/LTR

Learns from system usage.

Responsibilities:

* Context usage
* User feedback
* Accepted answers
* Rejected answers
* Explicit feedback for adaptive ranking (impressions are not training labels)

## Persistence

* **Qdrant:** `COLLECTION` is used by the indexer; `MEMORY_COLLECTION` is used
  by contextual-memory runtime traffic. Both are bootstrapped at startup.
* **JSON/JSONL:** global service state is rooted at `config.dataDir` (`DATA_DIR`)
  and written atomically.
* **Project index registry:** `.indexer-registry.json` intentionally belongs to
  the indexed project, not `DATA_DIR`.

## Bootstrap and readiness

Startup bootstraps both Qdrant collections, initializes learning state, and
loads the keyword index. Only then is the service marked bootstrapped. `/ready`
also checks Qdrant and Ollama/model availability; `/health` remains liveness
only.
